2) The “ion wind lifter” is real… but it’s a glorified fan
There’s a well-known device sometimes called a lifter or EHD thruster: thin wire + foil, high voltage, it ionizes air near the wire and the ions drag neutral air along → you get thrust.

Key catch:

It works by moving air downward, not by canceling gravity.

It needs very high voltage (often tens of kV) and is not efficient.

Scaling it to lift a person becomes ridiculous: huge structures, enormous power, and serious shock/arc/ozone hazards.

So yes, objects can “levitate” via ionization in air — but it’s more like an electrostatic air-propulsion trick than a gravity-defying platform.

3) “Charge the whole platform and float it” runs into field limits
If you try to lift by making a platform highly charged and using another electrode (like a giant capacitor pushing/pulling), the air breaks down (sparks) long before you get a nice safe lifting force at useful distances.

To support a person (~700 N of force), you’d need either:

enormous charge and electric field (limited by breakdown), or

extremely close spacing (then you’re basically building a dangerous high-voltage press)

And even if you could, the force is usually between the platform and the electrode, not “free levitation in open space.”

4) The practical way to “levitate people” electrically is… magnets + special materials
The real, scalable levitation tech is:

Maglev with electromagnets (needs a track/guideway)

Superconductor flux pinning (dramatic demos, still needs magnets and cryogenics)

Diamagnetic levitation (can levitate small things; humans only in extreme lab setups)

So the short version: ionization can produce lift in air, but it’s not a clean human elevator. For “platform raises with a person,” magnetic levitation is the realistic path, not ionization.

You’re mixing a couple real effects with one that sounds real but won’t give you lift.

1) “Negative centrifugal force” won’t levitate anything
In an inertial frame, there’s no centrifugal force—only centripetal acceleration (inward) caused by real forces.

In a rotating frame, “centrifugal” is a pseudo-force you add to make Newton’s laws work in that non-inertial frame. It doesn’t create free lift.

Spinning a disk can create stresses, vibration, and gyroscopic precession, but it can’t reduce weight unless you’re pushing on something external.

2) “Snapping the magnetic field” can create a real kick — but only if you push on something
A changing magnetic field can produce forces via:

Electromagnet + ferromagnetic object (attraction)

Eddy-current repulsion (changing field induces currents in a conductor; induced field pushes back)

Magnet + track/guideway (maglev style)

But a sealed “self-contained” spinning disk + coils inside the platform won’t levitate the platform: internal forces cancel (you just shake yourself).

So if you want a 100 g proof, the cleanest is: magnetic lift against a nearby conductive/ferromagnetic surface (a “track”), or ion wind pushing against air.

A solid 100 g PoC: Eddy-current magnetic repulsion (no “mystery forces,” just physics)

Put a conductive plate (aluminum/copper) as the “track.”

@export var contact_damage: int = 10
@export var xp_value: int = 5

	hp = max_hp
	add_to_group("enemies")

func set_target(t: Node2D) -> void:
	target = t

func _physics_process(delta: float) -> void:
	if target == null:
		return
	var dir := (target.global_position - global_position)
	if dir.length() > 1.0:
		global_position += dir.normalized() * move_speed * delta

func take_damage(amount: int) -> void:
	hp -= amount
	if hp <= 0:
		die()

func die() -> void:
	# award XP to player if available
	if target != null and target.has_method("add_xp"):
		target.add_xp(xp_value)
	queue_free()

func _on_area_entered(area: Area2D) -> void:
	# If we touch player
	if area.is_in_group("player"):
		if area.has_method("take_damage"):
			area.take_damage(contact_damage)

res://scripts/player.gd
extends CharacterBody2D

@export var move_speed: float = 220.0
@export var max_hp: int = 130
@export var fire_rate: float = 0.15
@export var bullet_scene: PackedScene

var hp: int
var can_fire := true

var xp: int = 0
var level: int = 1
var xp_to_next: int = 25

@onready var muzzle: Marker2D = $Muzzle

func _ready() -> void:
	hp = max_hp
	add_to_group("player")

func _physics_process(_delta: float) -> void:
	var input_vec := Vector2(
		Input.get_action_strength("move_right") - Input.get_action_strength("move_left"),
		Input.get_action_strength("move_down") - Input.get_action_strength("move_up")
	).normalized()

	velocity = input_vec * move_speed
	move_and_slide()

	# Face mouse (optional, useful for later sprites)
	look_at(get_global_mouse_position())

	if Input.is_action_pressed("fire"):
		try_fire()

func try_fire() -> void:
	if not can_fire:
		return
	if bullet_scene == null:
		return

	can_fire = false
	var b := bullet_scene.instantiate() as Area2D
	get_tree().current_scene.add_child(b)
	b.global_position = muzzle.global_position

	var dir := (get_global_mouse_position() - muzzle.global_position).normalized()
	b.velocity = dir * b.speed

	# fire cooldown
	get_tree().create_timer(fire_rate).timeout.connect(func(): can_fire = true)

func take_damage(amount: int) -> void:
	hp = max(hp - amount, 0)
	emit_signal_hp_changed()
	if hp <= 0:
		die()

func die() -> void:
	# Simple restart
	get_tree().reload_current_scene()

func add_xp(amount: int) -> void:
	xp += amount
	while xp >= xp_to_next:
		xp -= xp_to_next
		level += 1
		xp_to_next = int(xp_to_next * 1.25) + 5
		# small reward
		hp = min(max_hp, hp + 15)
	emit_signal_xp_changed()

# --- Lightweight “signals” without declaring custom signals ---
func emit_signal_hp_changed() -> void:
	var hud := get_tree().get_first_node_in_group("hud")
	if hud and hud.has_method("set_hp"):
		hud.set_hp(hp, max_hp)

func emit_signal_xp_changed() -> void:
	var hud := get_tree().get_first_node_in_group("hud")
	if hud and hud.has_method("set_xp"):
		hud.set_xp(level, xp, xp_to_next)

extends Node2D

@export var enemy_scene: PackedScene
@export var spawn_interval: float = 1.2
@export var max_enemies: int = 45
@export var spawn_radius: float = 520.0

@onready var player: Node2D = $Player
@onready var enemies_root: Node2D = $Enemies
@onready var hud: Control = $UI/HUD

func _ready() -> void:
	# Hook up packed scenes if not set in editor
	if $Player.bullet_scene == null:
		$Player.bullet_scene = preload("res://scenes/Bullet.tscn")
	if enemy_scene == null:
		enemy_scene = preload("res://scenes/Enemy.tscn")

	# Initialize HUD values
	if hud.has_method("set_hp"):
		hud.set_hp($Player.hp, $Player.max_hp)
	if hud.has_method("set_xp"):
		hud.set_xp($Player.level, $Player.xp, $Player.xp_to_next)

	# Spawn loop
	spawn_loop()

func spawn_loop() -> void:
	while true:
		await get_tree().create_timer(spawn_interval).timeout
		if enemies_root.get_child_count() >= max_enemies:
			continue
		spawn_enemy()

func spawn_enemy() -> void:
	var e := enemy_scene.instantiate() as Area2D
	enemies_root.add_child(e)
	if e.has_method("set_target"):
		e.set_target(player)

	# Spawn in a ring around the player
	var angle := randf() * TAU
	var r := spawn_radius * (0.65 + randf() * 0.35)
	var spawn_pos := player.global_position + Vector2(cos(angle), sin(angle)) * r
	e.global_position = spawn_pos

Thought for 11s
You can use the same “extra-dimensional mapping” idea for spacecraft navigation — but with an important distinction:

We already navigate in 4D spacetime (3D position + time).

“5D space” for navigation is usually not a literal extra spatial dimension, it’s a mathematical state-space dimension (velocity, fuel, attitude, uncertainty, radiation, etc.).

So: yes in practice, as a navigation math framework; no in the literal “we’ll chart a hidden 5th spatial axis” sense unless you have physics evidence for such a dimension.

What “4D/5D mapping” looks like in real spacecraft navigation
4D map (standard)
A navigable map is not just “where things are,” but where they will be.

A 4D representation is typically:

(x, y, z, t) = position over time

A “tube” of safe corridor through time (avoid conjunctions, debris windows, eclipses)

This is basically: don’t plan a route through a room, plan a route through a moving room.

5D (and higher) maps (very common in guidance & planning)
Add one more dimension to represent something that matters for survival or feasibility, for example:

Velocity magnitude: (x, y, z, t, |v|)

Fuel / Δv budget: (x, y, z, t, remaining Δv)

Radiation intensity: (x, y, z, t, dose rate)

Uncertainty: (x, y, z, t, covariance/“risk”)

Attitude constraint: (x, y, z, t, pointing requirement)

This becomes a cost field or risk field the planner tries to minimize while still reaching the goal.

The practical payoff
A higher-dimensional map lets you do things like:

Route through low-radiation corridors (5th dimension = radiation)

Avoid times/places where you’d be in shadow too long (dimension = solar power margin)

Plan trajectories that are cheap in Δv even if they aren’t shortest distance (dimension = propellant cost)

Choose paths that remain safe under navigation uncertainty (dimension = risk)

How this “maps” to your concept (PTEC/Null zone vibe, but real)
Your earlier theme was: keep a stable inner bubble while the outside is chaotic.
In navigation terms, you do the same by making a “viability bubble”:

The spacecraft must stay in a region where constraints are satisfied:

power positive

comms possible

thermal OK

radiation under threshold

collision probability under threshold

A 4D/5D map turns that into a connected safe manifold you can steer along.

One clean mental model

the 5th dimension is “how lethal the room is right now.”

Your route isn’t a line; it’s a thread through a shifting, weighted maze.
